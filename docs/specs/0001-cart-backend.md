# 0001 · Cart backend

**Status**: In Progress
**Date**: 2026-10-25

## Summary

This decision adds a persistent authenticated cart to the FastAPI backend.
Each cart item belongs to one Supabase Auth user and one product.
Postgres protects the user and product relationship, while atomic upserts prevent concurrent add requests from losing quantities.
The cart keeps quantities only, so the API always reads current product prices and stock.

## Context

> ⚠️ Premise note: `AGENTS.md` and `context/architecture.md` currently place carts in Redis. This task explicitly requires a Supabase Postgres table and Alembic migration. This spec replaces that cart storage direction, and the architecture context needs a later update before implementation.

The backend already verifies Supabase JWTs and exposes the authenticated subject as `CurrentUser.id`.
There is no `profiles` SQLAlchemy model, no profiles migration, and no automatic profile creation during signup or token verification.
Products use UUID primary keys and remain the source for price, stock, name, and availability.

## Requirements

1. **AC-1**: An authenticated user can read only their own cart and its current product details.
2. **AC-2**: An authenticated user can add a positive quantity to a product already in their cart without creating a duplicate item, including when requests arrive at the same time.
3. **AC-3**: An authenticated user can set an item quantity. A quantity of `0` removes that item.
4. **AC-4**: Cart quantities are positive integers, do not exceed `99`, and do not exceed the product stock at the time of the mutation.
5. **AC-5**: The API never accepts a user id, price, product name, or stock value from the client as cart data.
6. **AC-6**: Deleting a Supabase Auth user removes that user’s cart items.

## Options considered

1. **Postgres `cart_items` table, chosen.** It supplies foreign keys, a database uniqueness rule, migrations, and durable carts. It adds a database write for each cart mutation.
2. **Redis hash, the earlier project direction.** It is fast and supports expiry, but it does not meet this task’s Postgres table and Alembic requirements. It also needs separate work to preserve relational ownership guarantees.
3. **Create a `profiles` table first.** It could provide a local foreign key target, but no profile model, migration, or automatic creation flow exists today. Adding one would expand this cart decision into unfinished profile lifecycle work.

## Decision

Use Postgres as the cart store, with one `cart_items` row for each user and product pair.
The owner foreign key is `auth.users.id` because the required local profiles table and automatic profile row creation do not exist.
Use FastAPI’s existing `get_current_user` dependency for ownership, plus Postgres row level security as defense in depth.

**Implementation skills**: `architect` (`ArtisanLoft`, `.agents/skills/architect`) · `develop` (`ArtisanLoft`, `.agents/skills/develop`)

## Rationale

The application already gets the authenticated Supabase user id from a verified JWT, and Supabase Auth owns the matching UUID row in `auth.users`.
Referencing that row directly avoids an incomplete profiles dependency and ensures deletion cleans up cart rows automatically.
The composite uniqueness rule lets Postgres serialize writes for one user and product, which is the contention point for repeated add actions.
Redis remains suitable for cache and rate limit work, but it is not the cart source of truth under this decision.

## Feature design

**Data model sketch**:

| Table | Field | Type | Rules |
|---|---|---|---|
| `cart_items` | `id` | UUID | Primary key, generated by Postgres |
| `cart_items` | `user_id` | UUID | Required foreign key to `auth.users.id`, `ON DELETE CASCADE` |
| `cart_items` | `product_id` | UUID | Required foreign key to `products.id`, `ON DELETE RESTRICT` |
| `cart_items` | `quantity` | integer | Required, `1` through `99` |
| `cart_items` | `created_at` | timezone aware timestamp | Required, server default is current time |
| `cart_items` | `updated_at` | timezone aware timestamp | Required, updated on every mutation |

`cart_items` has a named unique constraint on `(user_id, product_id)`. Its leftmost `user_id` column also supports the user cart lookup, so a separate user index is not required.

Enable row level security on `cart_items` with policies that allow a Supabase authenticated role to select, insert, update, and delete only rows where `auth.uid() = user_id`. The FastAPI service must still enforce ownership because it accesses Postgres outside a direct browser to Supabase table flow.

**State transitions**:

```text
absent → present(quantity 1 to 99) → present(updated quantity 1 to 99)
present → absent, when PATCH quantity is 0 or DELETE succeeds
```

**Concurrency and quantity rules**:

1. `POST` is an atomic add operation. It uses one Postgres `INSERT ... ON CONFLICT (user_id, product_id) DO UPDATE` statement that adds the requested quantity to the committed row value.
2. The insert and conflict update both require the product to be active and the resulting quantity to be no more than the current product stock and `99`.
3. A conflicting write waits for the row lock held by the first write, then evaluates the new committed quantity. This prevents duplicate rows and lost increments.
4. `PATCH` sets an absolute quantity. Concurrent `PATCH` and `POST` operations serialize on the same row. The mutation that commits last determines the final absolute quantity when `PATCH` is involved.
5. Cart quantity does not reserve stock. Checkout must recheck active status, price, and stock and use its own atomic stock decrement.
6. `POST` accepts only a positive add quantity. `PATCH` accepts `0` through `99`, where `0` deletes the row. `DELETE` is idempotent and returns success even when the row is already absent.

**API surface**:

| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| `/api/v1/cart` | GET | None | `CartRead` | Bearer JWT | `401` |
| `/api/v1/cart/items` | POST | `product_id: UUID`, `quantity: int` from `1` to `99` | `CartItemRead` | Bearer JWT | `401`, `404`, `409`, `422` |
| `/api/v1/cart/items/{product_id}` | PATCH | `quantity: int` from `0` to `99` | `CartItemRead` or `204` when `0` removes it | Bearer JWT | `401`, `404`, `409`, `422` |
| `/api/v1/cart/items/{product_id}` | DELETE | Path `product_id: UUID` | `204 No Content` | Bearer JWT | `401` |

`CartRead` response shape:

```json
{
  "items": [
    {
      "product_id": "uuid",
      "quantity": 2,
      "product": {
        "id": "uuid",
        "slug": "oak-dining-table",
        "name": "Oak Dining Table",
        "image_url": "https://...",
        "price_cents": 2999900,
        "currency": "INR",
        "stock": 8,
        "is_active": true
      },
      "line_total_cents": 5999800
    }
  ],
  "item_count": 1,
  "total_quantity": 2,
  "subtotal_cents": 5999800,
  "currency": "INR"
}
```

`CartItemRead` is the matching item object in `items`. Product data is current at read time. Prices stay in integer paise. Routers use the project’s existing `HTTPException` response convention until a global error envelope is implemented.

**Value sourcing**:

| Action | Value produced or displayed | Source |
|---|---|---|
| Read cart | Cart owner | Verified JWT subject from `get_current_user` |
| Read cart | Item quantity and timestamps | `cart_items` columns filtered by authenticated `user_id` |
| Read cart | Product details, price, stock, currency, availability | Current `products` row joined by `product_id` |
| Read cart | `line_total_cents` | `products.price_cents * cart_items.quantity` |
| Read cart | `item_count` | Number of returned cart item rows |
| Read cart | `total_quantity` | Sum of returned `cart_items.quantity` values |
| Read cart | `subtotal_cents` | Sum of item `line_total_cents` values |
| Add item | Product and requested increment | Validated request `product_id` and `quantity` |
| Add item | New quantity | Atomic Postgres upsert using existing quantity and request quantity |
| Set item quantity | Product path key and target quantity | Validated path `product_id` and request `quantity` |

**Key invariants**:

1. A cart item belongs to exactly one Supabase Auth user and one existing product.
2. One user has at most one cart item row for each product.
3. Stored quantity is always an integer from `1` through `99`.
4. Client supplied ownership, price, product details, and stock values are ignored.
5. Add and set operations reject inactive products and a requested resulting quantity above current stock.
6. Cart reads always derive price and totals from current product data.
7. Cart writes filter by the verified JWT subject on every query.

**Security model**:

Every endpoint requires the existing Bearer JWT dependency. The router never accepts a user id in a path, query, or body. The service derives the owner from `CurrentUser.id` and includes it in every select, mutation, and delete predicate. Row level security mirrors that rule for direct Supabase access. This feature handles account identifiers only and introduces no payment or regulated data.

**Critical test scenarios**:

1. Happy path: a signed in user adds an active in stock product, then reads a cart with current product details and integer paise totals, verifies **AC-1**, **AC-2**, and **AC-5**.
2. Failure case: two simultaneous add requests for the same user and product produce one row with a correct combined quantity, and an add above current stock returns `409`, verifies **AC-2** and **AC-4**.
3. Quantity change: setting quantity to `0` removes the item, verifies **AC-3**.
4. Auth and permission: an unauthenticated request returns `401`, and a user cannot read, patch, or delete another user’s cart item, verifies **AC-1** and **AC-5**.
5. Lifecycle: deleting a Supabase Auth user cascades to that user’s cart rows, verifies **AC-6**.

## Build plan

1. Add the `CartItem` SQLAlchemy model, Pydantic request and response schemas, model import, and one Alembic migration with the foreign keys, check constraint, uniqueness rule, timestamps, and row level security policies, satisfies **AC-1**, **AC-4**, and **AC-6**.
2. Build a cart service that reads enriched cart data and performs conditional atomic upserts, absolute quantity changes, and deletion in short transactions, satisfies **AC-1**, **AC-2**, **AC-3**, **AC-4**, and **AC-5**.
3. Add and mount the `/api/v1/cart` router using `get_current_user`, with the routes and response shapes in this spec, satisfies **AC-1**, **AC-2**, **AC-3**, and **AC-5**.
4. Add backend tests for ownership, validation, concurrent adds, stock caps, deletion, totals, and cascade behavior, satisfies **AC-1** through **AC-6**.

## Consequences

**Positive**:

1. Cart ownership and item uniqueness are protected by the database as well as the API.
2. Carts persist without Redis expiry and can be inspected with ordinary database tools.
3. Concurrent adds for one item remain correct without application memory locks.

**Negative or tradeoffs**:

1. Every cart change writes to Postgres, so it has more database load than a Redis hash.
2. The cart does not reserve inventory. A later checkout can still fail when another buyer has consumed stock.
3. The database role and Supabase row level security policies must be tested together because FastAPI does not use the browser’s direct Supabase access path.

**Neutral**:

1. No new environment variables or third party credentials are required.
2. The existing architecture documents Redis as cart storage and needs a separate context update to reflect this accepted design after implementation.
